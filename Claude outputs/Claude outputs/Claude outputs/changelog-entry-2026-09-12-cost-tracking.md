**Verified:** each commit independently checked by Claude via `.git/logs/HEAD` + `origin/main` ref + direct source diff before being trusted (per the Working Agreement) — all four matched their specs byte-for-byte, zero deviations. Full live click-through by Bhimal, including reading the actual Firestore item documents directly (bypassing the UI) to prove the write path, confirmed all three scenarios: a fresh order snapshots real cost, editing an item's selection re-snapshots cost for the new selection, and pre-existing orders correctly show blank (not `0.00`) since they predate the fix.

**Changes:**
- **Per-item food cost snapshot (`273588f`)** — `confirmCheckout` and `editOrderItemSelection` now resolve each item's cost as `mainCost + addOnCost` (Main dish cost via a targeted, memoized `mains/{mainId}` lookup — same pattern as the existing `weekOverrideCache`/`getWeekOverride` — plus base/dhal/salad/beverage/dessert costs), frozen onto the item at order time so later catalog cost edits don't retroactively change historical figures. Admin-only, never shown to the customer.
- **Dish photo storage migration (`b79225f`)** — Meal Library Main dish photo upload moved from writing a base64 data-URL directly into Firestore to uploading to Firebase Storage (`dishPhotos/mains/{mainId}`, mirroring the existing entity-logo upload pattern) and storing the resulting download URL in the same `photoUrl` field (field name unchanged — only what populates it changed). Motivated by the real target scale surfacing mid-discussion: ~100 distinct dish photos, not a handful, which risked Firestore's 1 MiB per-document cap under the old base64 approach.
- **CSV Total Cost / Profit columns (`a11dd98`)** — Transactions CSV export gained "Total Cost (Rs)" and "Profit (before VAT) (Rs)" columns, computed from the new `cost` field. Blank (not `0.00`) for any item that predates this fix, per the established no-retroactive-rewrite rule.
- **fsOrders cost-passthrough fix (`5fabb6a`)** — the new columns showed blank for every order, including fresh ones, until this fix. Root cause: `Operations.tsx`'s `fsOrders` `useMemo` reshapes raw Firestore item docs into the shape the rest of the file uses via an explicit field-by-field allow-list (not a spread), and that list was never updated to include `cost` — so it was silently dropped in transit even though it was correctly written to Firestore. One-line fix: added `cost: it.cost,` to the mapping.

**Net result — a real lesson on trusting live-test results:** the blank-CSV symptom looked for a long time like the cost-snapshot fix itself was broken. Direct verification of the actual Firestore documents (a small `firebase-admin` script run against the emulator, bypassing the UI entirely) proved the write path was correct the whole time — the bug was two steps downstream, in a display-layer field-mapping function nobody thought to check first. Worth remembering: when a shipped, source-verified fix appears not to work live, checking the raw data directly (not just the UI) can save a lot of time chasing the wrong layer.

**Flagged, not blocking — dev environment note:** during this session's live testing, the local Firebase Emulator Suite (`npm run emulators`) was found to silently stop running (dropping back to a plain terminal prompt with no error message) if that terminal is interacted with while it's meant to stay up, or if it's shut down ungracefully — losing any data created since the last clean export (`--export-on-exit=emulator-data`, only written on a graceful Ctrl+C shutdown). Several rounds of "the fix isn't working" during today's testing turned out to be exactly this: the emulator had quietly stopped, so new test orders were never actually being written anywhere durable. Worth remembering for future sessions: confirm the emulator terminal is still genuinely alive (not just trust that it was started) before treating a live test result as meaningful, and always shut it down with a single clean Ctrl+C (waiting for "Export complete") rather than closing the window.
